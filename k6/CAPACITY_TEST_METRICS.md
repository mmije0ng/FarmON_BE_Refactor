# 용량 테스트 지표 가이드

`capacity-test.js` 실행 시 확인할 수 있는 주요 지표들입니다.

## 📊 기본 HTTP 지표 (k6 자동 수집)

### 1. 요청 성공/실패 지표

#### `http_req_failed` (에러율)
- **의미**: 전체 HTTP 요청 중 실패한 요청의 비율
- **형식**: `rate` (0.0 ~ 1.0)
- **목표값**: `< 0.01` (1% 미만)
- **해석**: 
  - 0.01 미만: 정상
  - 0.01 ~ 0.05: 주의 필요
  - 0.05 이상: 심각한 문제

#### `http_req_duration` (응답 시간)
- **의미**: HTTP 요청의 응답 시간 (밀리초)
- **통계값**:
  - `avg`: 평균 응답 시간
  - `min`: 최소 응답 시간
  - `max`: 최대 응답 시간
  - `p(50)`: 중앙값 (median)
  - `p(90)`: 90번째 백분위수
  - `p(95)`: 95번째 백분위수 ⭐ **가장 중요**
  - `p(99)`: 99번째 백분위수
- **목표값**: 
  - `p(95) < 2000ms` (2초 미만)
  - `p(99) < 5000ms` (5초 미만)
- **해석**:
  - p95가 2초 미만: 우수
  - p95가 2~5초: 양호
  - p95가 5초 이상: 개선 필요

#### `http_reqs` (요청 수)
- **의미**: 초당 요청 수 (RPS - Requests Per Second)
- **형식**: `rate` (요청/초)
- **해석**: 각 단계별로 목표 RPS를 달성했는지 확인

### 2. 사용자 관련 지표

#### `vus` (Virtual Users)
- **의미**: 현재 활성 가상 사용자 수
- **해석**: 각 단계별로 목표 사용자 수에 도달했는지 확인

#### `vus_max`
- **의미**: 최대 가상 사용자 수
- **해석**: 테스트 중 최대 동시 사용자 수

### 3. 데이터 전송 지표

#### `http_req_receiving` (응답 수신 시간)
- **의미**: 서버 응답을 받는 데 걸린 시간
- **해석**: 네트워크 대역폭이나 응답 크기 영향

#### `http_req_waiting` (대기 시간)
- **의미**: 서버가 요청을 처리하는 데 걸린 시간 (TTFB - Time To First Byte)
- **해석**: 서버 처리 성능의 핵심 지표

#### `http_req_sending` (요청 전송 시간)
- **의미**: 요청을 보내는 데 걸린 시간
- **해석**: 일반적으로 매우 짧음 (무시 가능)

#### `data_received` / `data_sent`
- **의미**: 수신/전송된 데이터 양 (바이트)
- **해석**: 네트워크 사용량 확인

## 🎯 커스텀 지표

### `errors` (커스텀 에러율)
- **의미**: `executeApiOperation()`에서 반환된 실패 비율
- **형식**: `rate` (0.0 ~ 1.0)
- **목표값**: `< 0.01` (1% 미만)

## 📈 용량 테스트에서 확인할 핵심 지표

### 각 단계별로 확인해야 할 지표

#### 1단계: 50명 유지 (3분)
```
✓ http_req_failed: rate < 0.01
✓ http_req_duration: p(95) < 2000ms
✓ http_reqs: 안정적인 RPS 유지
✓ errors: rate < 0.01
```

#### 2단계: 100명 유지 (3분)
```
✓ http_req_failed: rate < 0.01
✓ http_req_duration: p(95) < 2000ms
✓ http_reqs: 안정적인 RPS 유지
✓ errors: rate < 0.01
```

#### 3단계: 200명 유지 (3분)
```
✓ http_req_failed: rate < 0.01
✓ http_req_duration: p(95) < 2000ms
✓ http_reqs: 안정적인 RPS 유지
✓ errors: rate < 0.01
```

... (300명, 500명, 1000명, 1500명, 2000명도 동일)

### 최대 용량 판단 기준

**최대 용량 = 임계값을 넘지 않는 마지막 단계**

예시:
- 500명까지: 모든 지표 정상 ✅
- 1000명에서: `http_req_failed` > 0.01 또는 `p(95)` > 2000ms ❌
- **결론**: 최대 용량 = 약 500명

## 🔍 지표 해석 가이드

### 1. 에러율 (`http_req_failed`)
```
0.05% (25/5000) ✗
```
- **해석**: 5000개 요청 중 25개 실패 (0.05%)
- **판단**: 임계값 1% 미만이므로 양호하지만, 0%에 가까울수록 좋음

### 2. 응답 시간 (`http_req_duration`)
```
p(95)=2.3s  p(99)=4.5s
```
- **해석**: 
  - 95%의 요청이 2.3초 이내에 완료
  - 99%의 요청이 4.5초 이내에 완료
- **판단**: p(95)가 2초를 약간 초과하지만 양호한 수준

### 3. 요청 처리량 (`http_reqs`)
```
5.55/s
```
- **해석**: 초당 평균 5.55개 요청 처리
- **판단**: 사용자 수 대비 적절한 RPS인지 확인

### 4. 대기 시간 (`http_req_waiting`)
```
p(95)=2.2s
```
- **해석**: 서버가 요청을 처리하는 데 평균 2.2초 소요
- **판단**: 이 값이 전체 응답 시간의 대부분을 차지하는지 확인

## 🎯 단계별 성능 변화 추적

각 단계(50명, 100명, 200명 등)에서 다음을 비교:

1. **에러율 변화**: 단계가 올라갈수록 증가하는지?
2. **응답 시간 변화**: p(95), p(99)가 어떻게 변하는지?
3. **처리량 변화**: RPS가 사용자 수에 비례하여 증가하는지?
4. **대기 시간 변화**: 서버 처리 시간이 길어지는지?

## 📊 Grafana/Prometheus 연동 시 추가 확인 지표

k6가 Prometheus로 메트릭을 전송하는 경우, 다음 지표도 확인 가능:

- **EC2 CPU 사용률**: 서버 부하 확인
- **EC2 메모리 사용률**: 메모리 누수 확인
- **JVM GC 시간/빈도**: Java 애플리케이션 성능
- **Hikari 커넥션 풀**: 
  - `active`: 활성 커넥션 수
  - `idle`: 유휴 커넥션 수
  - `waiting`: 대기 중인 요청 수
- **RDS 커넥션 수**: 데이터베이스 부하
- **Slow Query**: 느린 쿼리 발생 여부

## 💡 실전 팁

1. **각 단계별로 결과를 별도로 기록**하여 비교
2. **임계값을 넘는 첫 단계**를 최대 용량으로 기록
3. **에러율과 응답 시간을 함께 고려**하여 판단
4. **단계 간 변화율**을 확인하여 성능 저하 패턴 파악
5. **네트워크 지연**을 고려하여 실제 서버 성능과 구분
